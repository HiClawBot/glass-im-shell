# GitHub Release Guide

Use this guide when preparing the first public GitHub release of Glass IM Shell.

## Before Creating The Public Repository

Confirm:

- Project name is `Glass IM Shell`.
- Public description uses original generic IM UI kit positioning.
- README preview art comes from `docs/assets/glass-im-shell-preview.svg`.
- Screenshots come from `output/smoke/` after running browser smoke.
- No generated screenshots, local logs, dependency folders, browser runner folders, or generated package archives are committed.
- No third-party product identity, official screenshots, official icon files, copied product text, product artwork, or real public-person likenesses are present.

## Repository Setup

When the final public repository exists:

1. Set the repository description to the same generic positioning used in `package.json`.
2. Add topics such as `im`, `chat`, `ui-kit`, `liquid-glass`, and `prototype`.
3. Enable issues.
4. Keep branch protection enabled for the default branch when available.
5. Require the `Verify` workflow before merging protected branches when available.
6. Use the issue and pull request templates already included in `.github/`.

## Metadata Update

Before publishing a package, update `package.json` with real public values:

- `repository`
- `homepage`
- `bugs`

Do not use placeholders. See `docs/PACKAGE_METADATA.md`.

After updating metadata, run:

```bash
npm run release:check
```

## Final Local Verification

Start local preview for human review:

```bash
npm run serve:local
```

Run:

```bash
npm run ci:verify
```

Review:

- `output/smoke/fullscreen-about.png`
- `output/smoke/mobile-wallet-transfer.png`
- `output/smoke/mobile-video-feed.png`
- `output/smoke/embedded-wallet.png`
- `output/smoke/host-api.png`
- `output/smoke/api-wallet-dark.png`
- `output/smoke/readme-preview.png`

Complete:

- `docs/PRE_RELEASE_ACCEPTANCE.md`
- `docs/PUBLICATION_READINESS.md`
- `docs/BETA_READINESS_REPORT.md`
- `RELEASE_CHECKLIST.md`
- `release-manifest.json`

## Commit And Tag

Use a focused release commit that includes:

- Runtime files.
- Examples.
- Schema.
- Documentation.
- Audit scripts.
- GitHub templates.
- CI workflow.
- Original preview asset.

Create tag:

```bash
git tag v0.1.0
```

Push the branch and tag only after local verification passes.

## GitHub Release

Create release `v0.1.0`.

Use `docs/RELEASE_DRAFT.md` as the release notes source.

Attach or reference:

- README preview asset.
- Smoke screenshots generated by this repository.
- Package preview result from `npm pack --dry-run`.
- Manifest audit result from `npm run audit:manifest`.

Do not attach:

- Dependency folders.
- Browser runner folders.
- Generated package archives unless intentionally publishing them as release artifacts.
- Local logs.
- Local operating system metadata.

## Optional Package Publish

Publish a package only after:

- Public repository URL fields are real.
- `npm run ci:verify` passes.
- `npm pack --dry-run` preview is accepted.
- `docs/PRE_RELEASE_ACCEPTANCE.md` is complete.
- Release boundary review passes.

If the package is published, confirm the package page shows:

- Correct name.
- Correct version.
- MIT license.
- README content.
- Public entry points.
- No unintended files.

## Post-Release Checks

After release:

- Confirm the `Verify` workflow passes on the public repository.
- Confirm issue and pull request templates render correctly.
- Confirm README images render.
- Confirm release notes match `docs/RELEASE_DRAFT.md`.
- Confirm package metadata points to the public repository when a package was published.
- Record any follow-up tasks in issues.

## Rollback Criteria

Prepare a follow-up release or unpublish only when allowed by the publishing platform and project policy if:

- Package contents include unintended local files.
- Public metadata points to the wrong repository.
- A release artifact includes restricted third-party materials.
- The package implies real wallet custody, signing, or live asset movement.
- The public README materially misstates the project scope.
